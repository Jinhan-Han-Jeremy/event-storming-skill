# 이벤트 스토밍 (텍스트판)

## 목적
사용자가 설명한 프로젝트를 "일어난 일" 중심으로 순서대로 정리한다.
그림을 그리는 것이 목적이 아니다. **놓치고 있는 것, 규칙끼리 부딪히는 것, 앞으로 생길 수 있는 문제를 미리 찾아 표로 정리하는 것**이 목적이다.
그리고 그 결과를 바탕으로 **이미 있는 기능과 새로 필요한 기능을 한 목록으로 정리**하고,
마지막으로 실제 개발에서 만들 **추정 도메인 디렉토리 표**를 만든다.

## 원칙
- 기능, 화면, 테이블이 아니라 **실제로 일어난 일**에서 출발한다.
- 어려운 용어를 쓰지 않는다. 아래 [용어]에 정한 말만 쓴다.
- 결과는 그림이 아니라 **표**로 낸다.
- 각 단계의 **규칙(개수, 형식, 기준)을 지킨다.** 지킬 수 없으면 그 사실을 이슈 표에 적는다.
- 이슈는 **점검 절차에서 나온 것만** 적는다. 개수를 채우려고 지어내지 않는다.
- 이 스킬에 나오는 예시는 모두 **표기 방법을 보여 주기 위한 것**이며 입력 프로젝트와 관계없다. 예시의 이름, 구조, 내용을 결과에 쓰지 않고, 내용은 **입력에서만** 가져온다.

## 용어
| 이 스킬에서 쓰는 말 | 뜻 | 쓰는 법 |
|---|---|---|
| 일어난 일 | 업무에서 실제로 벌어진 사건 | 과거형. "주문이 접수됨" |
| 행동 | 일어난 일을 만든 요청 | 명령형. "주문하기" |
| 유저 유형 | 행동을 하는 사람이나 역할 | "구매자", "판매자", "검수 담당자" |
| 자동 규칙 | 어떤 일이 일어나면 자동으로 다음 행동을 하는 규칙 | `A가 일어나면 → B 하기` |
| 보는 정보 | 유저가 행동하기 전에 확인하는 정보 | "장바구니 화면", "주문 내역" |
| 외부 서비스 | 우리가 직접 만들지 않고 연결해서 쓰는 서비스 | 결제, 택배, 본인 확인, 문자 |
| 전환점 | 흐름의 단계가 크게 바뀌는 일어난 일 | "주문이 확정됨", "발송됨" |
| 규칙 묶음 | 행동을 받아 규칙을 지키고 일어난 일을 만드는 단위 | "주문", "재고" |
| 지키는 규칙 | 규칙 묶음이 어떤 경우에도 깨지지 않게 보장하는 조건 | "재고는 0개 미만이 될 수 없다" |
| 상태 | 규칙 묶음이 거치는 단계 | "임시 저장", "공개", "삭제됨" |
| 업무 영역 | 같은 말을 같은 뜻으로 쓰는 업무 범위 | "판매", "배송", "정산" |
| 요청 | (5단계) 한 쪽이 다른 쪽에 "이걸 해 달라"고 보내는 것. 흐름 정리 표의 행동을 도메인 사이에서 부르는 말 | "이 수량만큼 예약해 줘" |
| 하는 일 | (5단계) 요청을 받은 쪽이 그에 반응해서 하는 활동 | 확인, 변경, 다른 도메인에 요청, 알림, 응답 |
| 도메인 | (5단계) 비슷한 책임을 모아 실제 개발 폴더로 만들 단위 | 영문 디렉터리 이름으로 쓴다 |

## 1단계. 프로젝트 관련 질문 리스트
이벤트 스토밍을 시작하기 전에 아래 질문지로 정보를 모은다.
- 사용자 설명에서 이미 답이 나온 항목은 채워 두고, **비어 있는 항목만** 한 번에 모아서 질문한다.
- 사용자가 "알아서 진행"이라고 하거나 답을 받을 수 없으면, 추측으로 채우고 답 앞에 `(가정)`을 붙인 뒤 진행한다.
- 모르는 항목은 "모름"으로 받아도 된다. "모름"인 항목은 이슈 표의 확인 질문으로 다시 올린다.

### 질문지
**1. 어떤 앱인가요?**
- 누가 어떤 불편을 겪는데, 이 앱이 그걸 어떻게 해결하나요? (한 문장)
- 돈은 어떻게 버나요? 누가 누구에게 언제 돈을 내나요?

**2. 누가 쓰나요?**
- 어떤 유형의 유저들로 구성돼 있나요? (예: 구매자, 판매자)
- 유저 유형마다:
  - 할 수 있는 일 / 하면 안 되는 일
  - 이 앱으로 얻는 것은?
  - "이게 되면 만족한다" 하는 순간은?
  - 가장 곤란해지는 상황은?

**3. 어떤 순서로 쓰나요? (유저 유형별)**
- 대표 흐름 1~3개를 처음부터 끝까지 순서대로 (예: 신청 → 확인 → 결제 → 받기)
- 각 단계는 사람이 직접 하나요, 자동으로 되나요?
- 대표 흐름 말고 유저가 쓰는 기능들 (예: 찜하기, 리뷰 쓰기, 문의하기, 내 정보 수정)

**4. 어떤 정보를 주고받나요?**
- 유저가 입력하는 정보
- 유저가 보거나 알림으로 받는 정보

**5. 얼마나 쓰나요?**
- 대략 몇 명이 쓰나요? (지금 / 1년 뒤 예상)

**6. 규칙**
- "~하면 ~한다" 규칙들
- 누군가의 확인이나 승인이 필요한 단계
- 취소, 환불 규칙

**7. 다른 서비스와의 연결**
- 연결해야 하는 외부 서비스 (결제, 택배, 본인 확인, 문자 등)

## 2단계. 이벤트 스토밍 진행 (10단계)
질문지의 **대표 흐름은 깊게**, **부가 기능은 가볍게**(2-1, 2-2, 2-5만) 다룬다.
아래 순서를 지키고, 각 단계의 **규칙**을 만족해야 다음 단계로 넘어간다.

| 단계 | 하는 일 | 규칙 | 놓치기 쉬운 것 |
|---|---|---|---|
| 2-1 일어난 일 모으기 | 질문지를 바탕으로 일어난 일을 순서 없이 적는다 | 전체 기준 **30~60개**. 모두 과거형 | 유저가 아닌 내부 직원과 자동 처리에서 일어나는 일 |
| 2-2 시간순 정렬 | 순서대로 늘어놓고 **정상 흐름**과 **실패·대안 흐름**을 나눈다 | 같은 일에 이름이 여러 개면 **하나로 합치고** 이슈 표에 남긴다 | 흐름이 중간에 끊기는 곳 |
| 2-3 문제 지점 표시 | 문제가 보이는 곳을 바로 이슈 표에 적는다 | 네 가지를 확인한다: **용어 충돌, 불분명한 규칙, 책임자가 없는 일, 돈·법 관련 위험** | 질문지에서 "모름"으로 남은 항목 |
| 2-4 전환점 찾기 | 흐름의 단계를 바꾸는 일어난 일을 골라 구간을 나눈다 | **3~7개** | 전환점마다 실패·취소 흐름이 있는지 |
| 2-5 행동과 유저 유형 | 일어난 일마다 **누가 + 어떤 행동**으로 만들었는지 붙인다 | 모든 일어난 일에 유저 유형이나 자동 규칙 중 하나가 붙어야 한다 | 해도 되는지 권한이 불분명한 행동 |
| 2-6 자동 규칙 | 일어난 일이 다음 행동을 자동으로 일으키는 규칙을 붙인다 | 형식 고정: `A가 일어나면 → B 하기` / 조건이 있으면 `A가 일어나고 [조건]이면 → B 하기` | 다음 행동이 없는 일어난 일 |
| 2-7 보는 정보 | 사람이 행동하기 전에 확인하는 정보를 붙인다 | 사람이 하는 행동마다 **1개 이상** | 판단에 필요한데 보여 주지 않는 정보 |
| 2-8 외부 서비스 | 외부 서비스와 맞닿는 행동과 일어난 일을 표시한다 | 연결 지점마다 **보내는 것과 받는 것**을 적는다 | 응답이 없거나 예상과 다른 결과가 올 때 |
| 2-9 규칙 묶음 | 행동을 받아 일어난 일을 만드는 단위로 묶는다 | 묶음마다 **지키는 규칙 1개 이상**과 **상태 목록**을 적는다. 지키는 규칙을 못 적으면 묶음이 아니므로 다른 묶음에 합치거나 보는 정보로 돌린다 | 한 규칙을 여러 묶음이 나눠 지키는 곳 |
| 2-10 업무 영역 나누기 | 규칙 묶음들을 업무 영역으로 나눈다 | 세 기준 중 **하나 이상**에 해당할 때만 경계를 긋는다: ① 전환점 ② 같은 말의 뜻이 바뀌는 곳 ③ 주로 쓰는 유저 유형이 바뀌는 곳 | 같은 말이 영역마다 다른 뜻으로 쓰이는 곳 |

### 흐름 정리 표 (2-1 ~ 2-8 결과)
| 구간 | 흐름 | 유저 유형 | 행동 | 일어난 일 | 자동 규칙 | 보는 정보 | 외부 서비스 |
|---|---|---|---|---|---|---|---|

- **구간**: 2-4에서 나눈 구간. 전환점인 일어난 일에는 ★을 붙인다.

- 해당하는 내용이 없는 칸은 비워 둔다.
- 일어난 일이 40개를 넘으면 **구간별로 표를 나눠** 출력한다.

|---|---|---|---|---|

### 업무 영역 표 (2-10 결과)
| 업무 영역 | 포함된 규칙 묶음 | 나눈 기준 (①②③) | 다른 영역에 알려 주는 일어난 일 |
|---|---|---|---|

## 3단계. 이슈 찾기 (이 스킬의 핵심)
네 가지 점검을 **순서대로** 모두 수행한다. 점검마다 보는 각도가 다르므로 하나도 건너뛰지 않는다.
2-3에서 적은 이슈와 각 단계 표의 "놓치기 쉬운 것"도 함께 확인한다.

### 3-1. 일어난 일 점검 (하나의 사건이 어긋날 때)
대표 흐름의 일어난 일마다 던진다.
- 이 일이 **안 일어나면**? (실패, 중단)
- 이 일이 **두 번 일어나면**? (중복 요청, 중복 결제)
- 이 일이 **늦게 일어나면**? (지연, 기한 초과)
- 이 일의 **순서가 바뀌면**? (취소가 결제보다 먼저 도착)
- **두 사람이 동시에** 하면? (마지막 1개 상품을 동시에 구매)
- **되돌려야 하면**? (취소, 환불, 반품)
- **하면 안 되는 사람이** 할 수 있나? (권한)

### 3-2. 상태 점검 (상태와 행동이 어긋날 때)
상태가 3개 이상인 규칙 묶음을 대표 흐름 중심으로 **최대 3개** 골라 아래 표를 만든다.
행에는 상태, 열에는 **그 묶음에 닿는 모든 행동**(다른 묶음의 행동 포함: 예를 들어 "글"에 닿는 좋아요, 댓글, 신고)을 둔다.
칸에는 `가능` / `불가` / `?`를 적는다. 입력에서 답을 찾을 수 없으면 `?`이고, **`?`는 모두 이슈 표에 올린다.**

| 상태 \ 행동 | 행동 A | 행동 B | 행동 C |
|---|---|---|---|
| 상태 1 | 가능 | 불가 | ? |

표 아래에 한 줄씩 확인한다.
- 모든 상태에 들어오는 행동과 나가는 행동이 있는가? (빠져나갈 수 없는 상태가 있으면 이슈)
- 상태가 바뀔 때 이미 붙어 있던 것(댓글, 좋아요, 알림, 외부 공개)은 어떻게 되는가?

### 3-3. 교차 점검 (두 가지가 서로 부딪힐 때)
아래 네 쌍을 서로 대조해 모순을 찾는다. 찾은 모순의 형태는 `충돌`로 적는다.
| 대조하는 쌍 | 찾는 것 | 예 |
|---|---|---|
| 규칙 ↔ 규칙 | 두 규칙을 동시에 만족할 수 없는 경우 | "비공개 즉시 제외" vs "출간 즉시 팔로워 알림" |
| 규칙 ↔ 유저의 곤란한 상황 | 규칙을 지키면 어떤 유저 유형이 곤란해지는 경우 | "출간은 승인 없이 즉시" vs 운영자의 "스팸 도배" |
| 유저 유형 ↔ 유저 유형 | 한 유형의 이익이 다른 유형의 손해가 되는 경우 | 운영사의 광고 수익 vs 독자의 "광고가 코드를 가림" |
| 할 수 있는 일 ↔ 하면 안 되는 일 | 행동을 조합하면 금지된 일을 할 수 있게 되는 경우 | "글 수정 가능" + "광고 스크립트 금지" → 본문에 스크립트를 넣을 수 있나? |

### 3-4. 유저 기대 점검 (질문지의 답이 흐름에 반영됐는지)
- 유저 유형마다 **"만족하는 순간"**이 흐름 정리 표의 일어난 일로 있는가? 없으면 `누락`.
- 유저 유형마다 **"곤란한 상황"**을 막거나 처리하는 흐름이 있는가? 없으면 `누락`.
- **"하면 안 되는 일"**마다 그것을 막는 규칙이나 상태가 있는가? 없으면 `누락`.

### 이슈 표
카테고리는 아래 중에서 고른다:
`유저·권한` / `흐름 순서` / `상태` / `실패·취소` / `시간·기한` / `돈·정산` / `정보` / `외부 서비스` / `규칙` / `용어` / `사용자 증가`

형태는 아래 중에서 고른다:
- `누락`: 있어야 하는데 없음
- `충돌`: 서로 맞지 않음
- `모호`: 뜻이나 기준이 불분명함
- `미래 위험`: 지금은 괜찮지만 나중에 문제가 될 수 있음

영향은 맨 앞에 등급을 붙인다:
- `[높음]`: 돈·데이터 손실, 법적 문제, 대표 흐름이 멈춤
- `[중간]`: 일부 유저나 부가 기능이 제대로 안 됨
- `[낮음]`: 불편하지만 우회 가능

| 단계 | 카테고리 | 형태 | 이슈 | 발생 상황 | 발생 시점 | 영향 | 확인 질문 |
|---|---|---|---|---|---|---|---|
| 3-1 | 실패·취소 | 누락 | 결제 실패 후 재고 처리 흐름 없음 | 결제가 실패했을 때 | 결제 요청 직후 | [높음] 팔리지 않은 상품이 품절로 보임 | 결제 실패 시 잡아 둔 재고를 언제 풀어야 하나요? |

- **발생 시점**은 흐름 안의 위치("결제 요청 직후")나 운영 시기("출시 직후", "사용자가 늘어날 때", "규칙을 바꿀 때")로 적는다.
- **확인 질문**은 사용자나 현업이 예/아니요 또는 짧게 답할 수 있게 쓴다.
- 같은 원인에서 나온 이슈는 하나로 합치고, 단계 칸에 모두 적는다 (예: `3-1, 3-2`).
- 이슈 표 아래에 **카테고리별 건수**를 한 줄로 적는다. 0건인 카테고리는 그 카테고리 관점으로 흐름을 한 번 더 보고, 그래도 없으면 "확인함, 없음"으로 적는다.

## 4단계. 필요 기능 정리
흐름 정리 표와 이슈 표를 재료로 필요한 기능을 한 표로 모은다. 새로 지어내지 않고 **두 표에 근거가 있는 것만** 적는다.

### 기능을 뽑는 곳
| 재료 | 뽑는 기능 | 구분 |
|---|---|---|
| 흐름 정리 표의 사람이 하는 행동 | 그 행동을 할 수 있는 기능 (예: "주문하기") | 이미 있음 |
| 흐름 정리 표의 보는 정보 | 그 정보를 보는 기능 (예: "주문 내역 보기") | 이미 있음 |
| 흐름 정리 표의 자동 규칙 | 자동으로 처리되는 기능 (예: "결제 완료 알림") | 이미 있음 |
| 질문지의 부가 기능 | 그대로 옮긴다 (예: "찜하기", "공지 보기") | 이미 있음 |
| 이슈 표의 이슈 | 이슈를 막거나 처리하는 기능 (예: "결제 실패 시 재고 되돌리기") | 새로 필요 |

### 규칙
- 기능 이름은 "~하기", "~보기"처럼 **유저가 할 수 있게 되는 일**로 쓴다. 화면이나 버튼 이름으로 쓰지 않는다. 자동 처리 기능은 명사형으로 써도 된다 ("새 계정 주문 횟수 제한").
- 같은 기능이 여러 곳에서 나오면 한 행으로 합치고 근거를 모두 적는다.
- 하나의 이슈에서 기능이 여러 개 나올 수 있다.
- 근거는 일어난 일이면 그 이름을, 이슈면 `이슈: ` 뒤에 이슈를 짧게 적는다.
- **모든 이슈는 기능 표의 근거로 한 번 이상 나오거나, 표 아래 "기능이 아닌 결정 사항"에 적는다.** 정책을 먼저 정해야 기능이 정해지는 이슈가 여기에 해당한다.

### 필요 기능 표
| 기능 | 근거 | 유저 유형 | 구분 |
|---|---|---|---|
| 주문하기 | 주문이 접수됨 | 구매자 | 이미 있음 |
| 결제 실패 시 재고 되돌리기 | 이슈: 결제 실패 후 재고 처리 흐름 없음 | (자동) | 새로 필요 |

- 정렬: `이미 있음`을 업무 영역 순서대로 먼저 두고, `새로 필요`는 근거 이슈의 영향 등급 순서([높음] → [낮음])로 뒤에 둔다.
- 표 아래에 `이미 있음 N개 / 새로 필요 N개`를 한 줄로 적는다.

### 기능이 아닌 결정 사항
| 결정할 것 | 근거 이슈 | 결정되면 생기는 기능 |
|---|---|---|
| 부분 환불을 허용할지 | 이슈: 여러 상품 중 일부만 취소하는 규칙 없음 | 허용하면 "일부 상품 환불하기" |

## 5단계. 추정 도메인 디렉토리 정리
2~4단계 결과(흐름 정리 표, 규칙 묶음 표, 업무 영역 표, 필요 기능 표)를 바탕으로, 실제 개발에서 만들 **추정 도메인 디렉토리 표**를 만든다.

### 만드는 방법 (출력하지 말고 머릿속으로만 진행)
1. 대표 흐름마다 시작 요청부터 끝 결과(일어난 일)까지 **어떤 요청이 오가는지 먼저** 정한다. 도메인은 나중에 정한다.
2. 요청 이름은 보내는 쪽의 의도("무엇을")로 짓고 "어떻게"는 넣지 않는다.
   (표기 예시: "이 수량만큼 예약해 줘" O / "수량 값을 빼 줘" X)
3. 요청을 받을 쪽은 **그 요청을 처리할 정보와 지키는 규칙을 가진 쪽**으로 정한다. 규칙 묶음이 1순위 후보다.
4. 상태를 꺼내 와서 밖에서 판단하지 않는다. 판단은 받는 쪽이 한다.
5. 업무 영역을 넘을 때는 직접 요청하지 않고 일어난 일로 알린다. 결과를 즉시 알아야 할 때만 예외로 둔다.
6. 같은 받는 쪽을 모아 도메인으로 정리한다. 받는 요청이 없는 도메인은 없애고, 서로 다른 이유로 바뀌는 책임이 섞이면 나눈다.

### 디렉토리 이름 규칙
- 영문 소문자 **단수 명사**. 여러 단어면 kebab-case. 프로젝트에 정해진 표기법이 있으면 그것을 따른다.
  (표기 예시: `invoice`, `delivery-slot`)
- 기술 이름이 아니라 **입력의 업무 용어**를 영어로 옮긴다. `service`, `manager`, `common`, `util`, `data`, `info`는 쓰지 않는다.
- 경로는 `<업무 영역>/<도메인>` 최대 2단계. 업무 영역 안에 도메인이 하나뿐이면 `<도메인>`만 쓴다.
- 같은 한글 용어가 업무 영역마다 다른 뜻이면 영문 이름도 다르게 짓는다.

### 추정 도메인 디렉토리 표
아래는 칸마다 무엇을 쓰는지 보여 주는 자리 표시다. 실제 표는 입력 프로젝트의 도메인 수만큼 행을 만든다.

| 디렉토리 경로 | 도메인 (한글) | 받는 요청 | 하는 일 (요청을 받고 반응하는 활동) | 아는 것 | 지키는 규칙 | 함께 일하는 도메인 |
|---|---|---|---|---|---|---|
| `<업무 영역>/<도메인>` 또는 `<도메인>` | 입력에서 쓰는 한글 용어 | 이 도메인이 받는 요청 전부 (보내는 쪽 의도로) | 요청마다 확인·변경·다른 도메인에 요청·알림·응답 중 무엇을 하는지 | 하는 일에 필요한 정보 | 이 도메인이 깨지지 않게 지키는 규칙 전부 | 요청을 주고받는 도메인의 디렉토리 경로 |

- 입력에 근거가 없는 칸은 앞에 `(가정)`을 붙인다.
- 표 아래에 한 줄씩만 적는다: 규칙 묶음과 달라진 도메인과 그 이유, 같은 규칙을 두 도메인이 나눠 지키는 곳(있으면).

## 6단계. 출력 전 자체 점검
- [ ] 일어난 일이 30~60개이고 모두 과거형이다 (범위를 벗어나면 이유를 이슈 표에 적었다)
- [ ] 전환점이 3~7개다
- [ ] 모든 일어난 일에 유저 유형이나 자동 규칙이 붙어 있다
- [ ] 모든 자동 규칙이 `A가 일어나면 → B 하기` 형식이다
- [ ] 사람이 하는 행동마다 보는 정보가 있다
- [ ] 규칙 묶음마다 지키는 규칙과 상태 목록이 있다
- [ ] 업무 영역마다 나눈 기준(①②③)이 적혀 있다
- [ ] 3-1 ~ 3-4를 모두 수행했다
- [ ] 상태 표의 `?`가 모두 이슈 표에 있다
- [ ] 질문지에서 "모름"인 항목이 모두 이슈 표에 있다
- [ ] 흐름 정리 표의 사람이 하는 행동, 보는 정보, 자동 규칙과 질문지의 부가 기능이 모두 기능 표에 `이미 있음`으로 있다
- [ ] 모든 이슈가 기능 표의 근거나 "기능이 아닌 결정 사항"에 있다
- [ ] 흐름 정리 표의 대표 흐름 행동이 모두 어느 도메인의 "받는 요청"에 있다
- [ ] 디렉토리 이름이 이름 규칙(영문 소문자 단수, kebab-case, 금지 이름 없음, 최대 2단계)을 지킨다
- [ ] 예시에 나온 이름이나 내용이 결과에 섞이지 않았다
- [ ] 디렉토리 이름을 빼고는 어려운 용어 없이 [용어]에 정한 말만 썼다

하나라도 실패하면 고친 뒤 출력한다.

## 최종 출력 순서
1. 질문지 표 (1단계)
2. 흐름 정리 표, 규칙 묶음 표, 업무 영역 표 (2단계)
3. 상태 표 (3-2)
4. 이슈 표 (3단계): 영향 등급 순으로 정렬, 아래에 카테고리별 건수
5. 필요 기능 표와 기능이 아닌 결정 사항 (4단계)
6. 가장 먼저 확인해야 할 질문 3개
7. 추정 도메인 디렉토리 표 (5단계): 맨 마지막에 출력
